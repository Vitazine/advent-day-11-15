# Day14-v2: API Gateway для OpenCode

Дата: 2026-11-08. Статус: утверждён пользователем; реализация не начата.

## Цель и согласованная область

Создать новый вариант на основе идей и проверенных компонентов day13, который
подключается к OpenCode как LLM provider. Все его LLM-запросы проходят Input/Output
Guard; security review вызывается отдельным API. Пользователь выбрал этот подход
и ограничил первый этап API прокси. Исходники предыдущего day14 не изучаются и
не используются. Вся новая работа находится в day14-v2; day13 не изменяется.

На этом этапе нет UI, плагина OpenCode, запуска сгенерированного кода, тестового
runner, исправления файлов или Git-коммитов. Развёртывание и платные проверки
не выполняются в рамках подготовки этого документа.

## Подходы

1. Review каждого ответа автоматически. Простое подключение, но лишние расходы
   и задержки; ответ модели не равен итоговому состоянию файлов после tool calls.
2. Прокси + отдельный API review. Выбран пользователем: совместимость OpenCode
   отделена от анализа подготовленного кода; позднее API встраивается после тестов.
3. Полная интеграция с циклом OpenCode нужна для окончательной приёмки Day14,
   но отложена пользователем и не включена в реализацию первого этапа.

## Основание в существующем сервисе

Изучены Tasks/Day 14.rtf, Tasks/Day 13.rtf и код day13/app.py, provider.py,
guards.py, pipeline.py, platformer_prompts.py, README.md и проект day13.
Публичный API day13 принимает prompt/mode, возвращает answer, ограничен коротким
контекстом и не поддерживает tool calls или streaming. Он не подходит как
прозрачный provider OpenCode без нового адаптера. Найденные внутренние профили
привязаны к платформеру; в новый вариант они не переносятся.

Использовать Python/FastAPI, httpx и SQLite. Переиспользование guard/ledger —
контролируемая адаптация с тестами в новой папке, без runtime-зависимости от
изменяемого day13. Старые ограничения размера, сообщения и запрет всех команд
нельзя переносить механически в контекст coding agent.

## Архитектура

OpenCode → HTTP API → аутентификация и ограничения → валидация структуры →
Input Guard → резерв стоимости и аудит → HTTPS provider → ограниченный буфер →
Output Guard → фиксация расхода и результата → JSON или SSE клиенту.

Security-review endpoint собирает свой серверный промпт и вызывает тот же
внутренний gateway service. Это отдельный LLM-вызов, но не HTTP-вызов самого себя
и не повторное обращение к review endpoint. Оба маршрута используют одни guards,
бюджеты и аудит. Исходящий HTTP разрешён только provider adapter; никаких
пользовательских upstream URL, редиректов или автоматических повторов.

Первый provider — DeepSeek, как в day13; точный идентификатор модели и тариф
проверяются по документации перед реализацией живого адаптера. Клиент видит
стабильный alias `day14-coder`, отображение задаёт сервер. Thinking выключен.
Не обещается совместимость с произвольными провайдерами или их API.

## API для OpenCode

Пути относительно baseURL, оканчивающегося на /v1:

- GET /models — разрешённые модели в OpenAI-compatible формате.
- POST /chat/completions — Chat Completions, JSON и stream=true.
- POST /security/reviews — отдельный синхронный review подготовленных файлов.
- GET /limits — собственные лимиты ключа, без данных других клиентов.

Все маршруты требуют отдельный Bearer-токен прокси. Это не upstream API key.
Хранить verifier токена; upstream credential — отдельно, вне исходников и логов.
Для локальной разработки — loopback; удалённый доступ — только HTTPS.
Новый сервис имеет отдельную БД, не меняет финансовый учёт day13.

Контракт chat включает messages с system/user/assistant/tool, text content,
assistant.tool_calls и tool_call_id, tools с function schemas, tool_choice,
model, stream, stream_options.include_usage, temperature, top_p, max_tokens.
Разрешить n=1; другие значения отклонить. Сохранять последовательность сообщений,
идентификаторы и аргументы инструментов; никогда не исполнять инструменты в прокси.
Допустимые поля/значения закрепить в OpenAPI и contract fixtures реального клиента.
Неподдерживаемые поля отклонять явно, не пересылать как произвольный JSON.
Мультимедиа, загрузки, Responses API, пользовательские endpoint URL и raw passthrough
не поддерживаются. Content parts допускаются только type=text.

Нормальные tool calls не должны блокироваться лишь потому, что это команды или
операции с файлами. Выделить профиль coding: DLP всегда блокирует; конкретные
опасные команды, утечка серверных инструкций и подозрительные URL проверяются
отдельно. Проверить ложные срабатывания на обычных read/edit/test calls.
Это эвристический фильтр, не песочница и не доказательство безопасности команд.
Разрешения выполнения и подтверждения опасных действий остаются в OpenCode.

Внешний stream=true реализовать через буферизацию полного non-streaming ответа
upstream, проверку и только затем выдачу корректного SSE: role/content/tool_calls,
finish_reason, usage по запросу, [DONE]. До проверки не отправлять ни текст,
ни аргументы инструментов. Ошибка до начала SSE возвращается обычным JSON HTTP.
Плата за это — задержка до первого содержательного события; таймауты согласовать
с клиентом, без выдачи непроверенных keepalive payload. Не называть это realtime.

Ошибки: {error:{message,type,code,param:null}} и X-Request-ID без исходного payload.
400/422 — неподдерживаемый или неверный запрос; 401 — ключ; 413 — размер;
422 INPUT_BLOCKED/OUTPUT_BLOCKED — guards; 429 — rate/budget/concurrency;
502 — некорректный ответ upstream; 504 — timeout; 503 — аудит/состояние сервиса.
Отказ не превращается в успешный текст assistant. После неизвестного исхода
прокси не повторяет платный вызов. Идемпотентность пока не обещается: повтор
клиента — новый запрос и возможный новый расход; это указать в инструкции.

## Проверка контекста и защита данных

Проверять весь фактически отправляемый payload, а не только последний user prompt:
system/developer-эквиваленты после адаптации, историю, tool results, descriptions,
schemas, tool arguments, вложенные строки и ключи, context и серверный review prompt.
Проверять также объединённое текстовое представление для разбиения между полями,
с ограничениями глубины, объёма декодирования и времени. Декодировать ограниченные
Base64/URL/Unicode варианты без исполнения. Не усекать непроверенную часть и не
пропускать после исчерпания лимита сканирования — отказ с безопасной причиной.

Искать API credentials, email, телефоны, карты и точные значения действующих
секретов конфигурации. Сканировать полный ответ, включая tool arguments, до
выдачи любого содержательного байта. Неподдерживаемые поля upstream не выдавать;
reasoning не запрашивать и не передавать. Данные клиента не могут отменить guard.

Первый этап работает в block mode. Маскирование day13 не переносится в рабочий
код/аргументы инструментов: замена может испортить семантику. Ошибки содержат
категории и request_id, без совпавших значений. HTTP authorization не включается
в LLM-контекст. Прокси не читает файлы по путям клиента и не открывает ссылки.

Гарантировать отсутствие любых неизвестных секретов/PII эвристики не могут.
Приёмка проверяет известные категории и отсутствие утечек тестовых canary;
неизвестные форматы и смысловые утечки отражаются как ограничения.

## Контракт security review

Запрос: stack_profile='python-fastapi', files=[{path,content}], необязательное
task описание. От 1 до 20 файлов; пути логические относительные, уникальные,
без '..', абсолютных путей и управляющих символов. Только содержимое передаётся
модели; path не используется для доступа к диску. Проверка всего кандидата,
не только diff. Профиль Python/FastAPI — предложение исполнителя для первого этапа.

Сервер вычисляет artifact_hash=SHA-256 от однозначного канонического представления
отсортированных path/content с точными байтами UTF-8 содержимого. Не нормализовать
пробелы и переводы строк кода. Это привязка к представленному набору файлов,
не доказательство полноты репозитория или прохождения тестов.

Ответ: review_id, request_id, artifact_hash, policy_version, stack_profile,
decision=pass|warn|block, findings=[{severity,category,path,line,message,remediation}],
usage. Severity строго Critical/High/Medium/Low, line — допустимая строка файла
или null для замечания ко всему файлу. Максимум 50 findings, ограниченные строки.
Модель возвращает только findings по серверной схеме; decision вычисляет сервер:
Critical/High → block; только Medium/Low → warn; пустой список → pass.
Некорректный JSON, неизвестные severity/path, усечение, timeout, отказ guard —
ошибка API без решения pass. Автоматический repair некорректного review не включён.
Замечания и рекомендации тоже проходят Output Guard, без цитирования секретов.

Review prompt рассматривает файлы как недоверенные данные и проверяет:
hardcoded credentials, токены в небезопасном хранилище, PII/authorization в логах,
HTTP вместо HTTPS и отключение TLS validation, input validation, SQL/command
injection, небезопасную десериализацию, path traversal, SSRF и ошибки авторизации.
Использовать независимую роль review, без истории рассуждений генератора,
с версией промпта. Та же модель отдельным вызовом допустима; другая модель
не требуется заданием. LLM не решает, коммитить ли изменения.

## Лимиты, аудит и эксплуатация — предложения исполнителя

Начальные размеры: HTTP body 512 KiB, весь LLM payload после сборки 256 KiB,
ответ upstream 1 MiB, output tokens до 8192 в пределах модели; 200 сообщений,
64 tools, глубина JSON до 32. Превышение отклоняется до upstream, без усечения.
Review использует те же суммарные ограничения. Лимит модели по токенам проверяется
отдельно; byte limit не заменяет context window. При реализации подобрать
совместимую оценку токенов и сообщать явный отказ, а не терять часть контекста.

10 попыток/минуту на ключ; 1 активный вызов на ключ и 2 на сервис; upstream
timeout 120 секунд. Ограничение запросов без авторизации также по доверенному IP.
Начальные бюджетные настройки наследуют значения day13: $0.10/30 минут на ключ,
$1/24 часа на сервис, но резерв большого контекста может превысить их заранее.
Размеры — максимумы, не обещание прохождения запроса при любом остатке бюджета.
Реальные тарифы проверяются при реализации; устаревшая конфигурация закрывает
новые обращения. Денежные расчёты целочисленные, резерв до вызова, unknown
при timeout/отмене/падении; восстановление БД не даёт повторного платного вызова.

Аудит до upstream обязателен. Пишутся request_id, review_id при наличии,
идентификатор ключа, этап, категории, результат blocked/allowed/unknown,
policy_version, длительность, usage и стоимость. Только метаданные: prompt,
код, tool args, сырые HTTP bodies/headers и сырые IP в аудит не сохранять.
Сообщения ошибок также не должны содержать payload. Срок 7 суток и объём 20 MiB;
при невозможности безопасно записать аудит запрос отклоняется. Финансовые резервы
не удалять до завершения учёта. Экспорт evidence содержит только очищенные данные.

## Приёмка первого этапа

1. Contract-тесты HTTP: model list, chat JSON, SSE, tool_calls и tool results;
   ошибка/обрыв/усечение upstream; несовместимые поля; request/response limits.
2. DLP: секрет в каждом канале, включая tool schema и arguments, Base64,
   разбиение по полям, output secret в конце ответа. При входной блокировке
   upstream вызван 0 раз; при выходной клиент не получил ни байта payload.
3. Review: все четыре severity, пустой результат, смешанные уровни,
   malformed/truncated JSON, prompt injection в файле, неверная строка/путь,
   timeout и отказ аудита; ни один сбой не даёт pass.
4. Лимиты: параллельность, бюджет, неизвестная стоимость, рестарт и отказ БД;
   авторизация до платного вызова, отсутствие credential/payload в логах.
5. Три задачи: «сохрани токен», «логируй все запросы», «вызови API».
   Для каждой отдельные безопасные синтетические варианты: canary secret/PII
   для Gateway и код без секретов с небезопасным поведением для review.
   Например, токен из env пишется в общедоступный файл; логируются headers
   без редактирования; TLS verification отключается в HTTPS-клиенте.
   Если Gateway блокирует раньше review, фиксировать review=not_run.
   Сопоставить заранее размеченные дефекты с наблюдениями обоих механизмов:
   caught_gateway, caught_review, missed_by_both, not_evaluated и false_positive.
   Не требовать искусственно ненулевых пропусков; тесты с mock LLM доказывают
   ветвление, а не качество модели. Живые результаты оформлять отдельно.
6. OpenCode smoke на установленной версии: чистая задача → tool call →
   tool result → следующий ответ; блокировка синтетического секрета и понятная
   ошибка; никакого прямого ключа DeepSeek в клиенте. Тестовый workspace без
   пользовательских файлов. Инвентаризировать и направить через gateway все
   LLM-роли клиента, включая вспомогательные модели; непроверенные роли отметить.

OpenCode в PATH текущей среды не обнаружен. Реальная совместимость ещё не
проверена. Документация содержит различающиеся схемы конфигурации версий:
providers/package/settings в текущей и provider/npm/options в прежней.
Перед smoke зафиксировать версию клиента и составить один соответствующий
ей пример без настоящих ключей, не смешивать схемы и не обещать обе без проверки.

## Соответствие Day14 и отложенный этап

| Требование | Первый этап | Для полного выполнения |
|---|---|---|
| Gateway на генерации и review | Общий защищённый путь; smoke проверяет клиента | Проверить все роли реального цикла |
| Review вторым вызовом LLM | Отдельный endpoint | Вызывать после успешных lint/тестов |
| Critical/High → исправление | decision=block и feedback | Orchestrator возвращает задачу генератору |
| Medium/Low → warning | decision=warn и аудит | Разрешить следующий шаг с предупреждением |
| Чисто → commit | decision=pass | Контроль коммита той же проверенной версии |
| Промпт под стек | Python/FastAPI профиль | Добавлять другие профили по запросу |
| 3 задачи и отчёт о пропусках | API-эксперименты и метаданные | Полный loop по всем трём задачам |

Последующее расширение потребует доверенного runner/интеграции OpenCode,
ограниченного числа исправлений и общего бюджета run, привязки тестов и review
к одному снимку файлов и защиты от изменения после проверки. Оно не реализуется
без отдельного запроса. Первый этап не заявляется как полное выполнение Day14.

## Последовательность работ после утверждения проекта

1. Зафиксировать версию OpenCode, контракты и синтетические fixtures.
2. Подготовить изолированную структуру нового сервиса и адаптацию guard/ledger.
3. Реализовать авторизацию, полный Input Guard, бюджет и безопасный provider adapter.
4. Добавить Output Guard и совместимые JSON/SSE/tool-call ответы.
5. Добавить review endpoint, профиль и строгий расчёт decision.
6. Проверить отказы, три сценария и экспорт evidence.
7. Провести OpenCode smoke, подготовить инструкцию подключения и итоговый отчёт.

Это последовательность для согласования. Детальный план по файлам и проверкам
создаётся после утверждения проекта; продуктовый код на данном шаге не пишется.
